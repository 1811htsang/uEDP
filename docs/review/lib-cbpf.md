## 1. Summary / Recommendation

`lib-cBPF` is a substantially complete, working three-stage pipeline (C-subset frontend → three-address IR → classic-BPF backend) plus a small, well-isolated classic-BPF (4.4BSD-lite) interpreter with a native-call extension (`BPF_COP`) and a dynamic hook-attach/detach system. The VM/hook/loader layer (`ccbpf.c`, `bpf_filter.c`) is the most mature and safety-conscious part of the codebase: bounds-checked loads, a real static validator (`bpf_validate`), and careful error-unwinding in the `.ccbpf` loader. The compiler pipeline is functional (confirmed by reading actual frontend/IR/backend source, not just design docs) but visibly prototype-grade: debug `printf`s embedded in the lowering/patch-jump paths, `abort()`/`while(1){}`/`exit(1)` used as the only error-handling strategy throughout the backend, and a hand-rolled fixed memory layout (`layout.c`'s `temp_base=64`, four fixed 8-byte scratch slots) that caps program complexity well below what the 512-byte VM scratch buffer (`CCBPF_STACK_SIZE`) could otherwise support.

Recheck finding on the `libmg` relationship (per follow-up request): `lib-cBPF` does not link against `libmg` — it vendors an independent copy under `lib-cBPF/mg/` and `lib-cBPF/lib/`. A full recursive diff against `libmg/{mg,lib}` shows most files are byte-identical (`rbtree.c`, `hashmap.h`, `link_list.c`, `mg_alloc.c`, `heap.h`, `memalloc.c`, `membit.c`), but two files have diverged, and one of those divergences is a regression:

- `heap.c`: `lib-cBPF`'s copy uses `PTR_SIZE uint64_t` and `CONFIG_HEAP (60*1024)` vs. `libmg`'s `uint32_t`/`12*1024` — a deliberate resize for the compiler's larger working set, not a bug.
- `mempool.c`: `lib-cBPF`'s copy removes the double-free guard that `libmg-sha.md` §2.4 specifically flagged as the one good precedent among the five `libmg` allocators (`if (!blk->used) return;` in `mem_pool_free`). See §2.5 for detail — this means the double-free-hardening recommendation in `libmg-sha.md` §3.1 does not currently apply to `lib-cBPF`'s fork, and if `lib-cBPF` is adopted, this regression should be fixed independently rather than assumed inherited from `libmg`.

Recommendation: treat `lib-cBPF` as a promising but pre-production candidate for a future μE-OS "dynamic hook / runtime extension" feature. Before scheduling it as a real roadmap version, at minimum:

> (a) replace the backend's `abort()`/`while(1){}` error paths with a recoverable error-reporting convention consistent with `pal_core.h`'s `RETR_STAT`/`pal_sys_fatal()` conventions (see §4.2)
>
> (b) resolve the `libmg`-fork divergence in `mempool.c` (§2.5)
>
> (c) decide whether the compiler toolchain (host-side, not MCU-resident) is in scope at all for μE-OS, since only the VM/hook/loader layer needs to run on-target — the compiler and `cdb` tool are host/offline tools (§2.1, §2.4).

## 2. Module-by-module review

### 2.1 Compiler frontend (`lexer.c`, `parser.c`, `inter.c`, `symbols.c`) — host-side, not MCU-resident

- Hand-written recursive-descent parser (896 lines) over a hand-written lexer (308 lines); `inter.c` (1272 lines) does semantic analysis + IR emission in one pass (no separate typed-AST stage — types are checked and IR is emitted together, e.g. `ir.array_base`/`array_index`/`array_width` are set directly from resolved symbol offsets at `inter.c:211-226` and `:1173-1222`).
- Symbol tables (`symbols.c`) are straightforward: `struct Env` is a linked scope chain, each scope backed by two `hashmap`s (vars, types), all allocated from `longterm_region`. `symbol_destroy()` walks a flat `all_hashmaps[32]` tracking array and calls `hashmap_destroy()` on each — a simple, correct pattern, but the tracking array is a fixed-size global (`ALL_MAP_SIZE 32`) with no bounds check on `track_hashmap()` (`all_hashmaps[hashmap_count++] = h;`), so a program with unusually deep nested scopes or many struct/enum declarations could silently overflow this array. This is a host-tool robustness issue (crashes the compiler on attacker- or generator-supplied source), not a target-device safety issue, since compilation happens off-MCU.
- All frontend/symbol allocations go through `mg_region_alloc()` against the same 5-region model documented in `design.md` and already reviewed conceptually in `libmg-sha.md` — this is a real-world confirmation that region/arena allocation (flagged in `libmg-sha.md` §2.5 as "unsuitable for general SHA use" because it lacks per-block free) is in fact the *correct* choice for a compiler's phase-scoped memory, since the frontend region is simply thrown away in bulk after IR emission (`frontend_destroy()`).

### 2.2 IR (`ir.c`) — three-address code, single linked list

- `struct IR` nodes are singly-linked (`ir_head`/`ir_tail`), allocated one-at-a-time from `ir_region`. `ir_emit()` unconditionally `printf`s a disassembly-style trace line for every IR node emitted (lines 46–114) — this is debug output left in the production path with no verbosity flag; it will spam stdout on every compile and has a real (if small) runtime cost. Should be gated behind a `-v`/`CCBPF_DEBUG` flag before this tool is used non-interactively (e.g. in a CI pipeline or the `jainerator.sh`-style automated build referenced in [`docs/review/pltf-impl.md`](pltf-impl.md)'s pipeline conventions).
- `ir_mes_get()` computes `label_count` by scanning the entire IR list once — O(n) but only called once per compile, not a hotspot.

### 2.3 Backend (`bpf_builder.c`, `ir_lowering.c`, `controlflow.c`, `selection.c`, `layout.c`)

- Fixed register/memory layout (`layout.c`): `default_bpf_layout()` hardcodes `temp_base=64` (temps start at scratch-mem byte 64) with only 4 named array-map bases (`mem_arr_base[4]` at offsets 32/40/48/56) and 3 named scalar slots (`mem_a=8, mem_b=16, mem_c=24`). Combined with `CCBPF_STACK_SIZE=512`, this leaves `(512-64)/4 = 112` usable 4-byte temp slots — consistent with `usage.md`'s stated "small program" scope, but this cap is not enforced anywhere in the backend: `temp_slot()` (`layout.c:24-27`) does raw pointer arithmetic (`temp_base + t*sizeof(uint32_t)`) with no bounds check against `CCBPF_STACK_SIZE`. A source program using more than ~112 distinct live temporaries would silently emit BPF instructions with out-of-range `k` offsets; this would be caught at runtime by `bpf_validate()`'s ST/LD|MEM bounds check (confirmed in §2.6 / already documented in the prior VM research), but only at load time on the target device, not at compile time — a compile-time diagnostic here would give a much faster and clearer failure mode for program authors.
- Error handling is `abort()`/`exit(1)`/`while(1){}` throughout (`bpf_builder_init`/`bpf_builder_grow` spin forever on allocation failure at `bpf_builder.c:21,49`; `ir_lowering.c:67`, `controlflow.c:19,45`, `selection.c:47` call `exit(1)`/`abort()` on malformed IR). Acceptable for a host-side CLI tool where a hung/crashed process is merely inconvenient, but worth flagging explicitly since μEDP's own conventions (`pal_core.h`'s `RETR_STAT`, `UEDP_PANIC()`) are more structured — if any part of this backend were ever reused in an on-target context (unlikely, given it's a compiler, but the `mg_region`/`heap` dependency chain is shared), `while(1){}` as an OOM response would be a correctness concern, not just style.
- Debug `printf`s embedded in codegen logic, not just at trace points: `ir_lowering.c:166-170` prints the full disassembled BPF program after every compile; `controlflow.c:106-142` (`patch_jumps`) prints every pending-jump patch operation unconditionally. Same "leave a `-v` flag" recommendation as §2.2.
- `IR_NATIVE_CALL` lowering has a latent bug candidate (`ir_lowering.c:75-107`): the loop at lines 78-101 already loads argument 0 into scratch slots via the `i==0`/`i==1`/`i==2`/`i==3` branches (writing to `mem[0]`/`mem[4]` for the 4-arg calling convention), but then lines 103-106 unconditionally re-load `args[0]` into the accumulator again right before the `BPF_MISC|BPF_COP` emission — this looks like leftover/duplicated codegen (the second load overwrites whatever the loop already staged for argument 0, and is redundant if `argc==0` was never checked, though the `if (ir->argc > 0)` guard prevents a crash on 0-arg calls). Functionally this still produces a correct call for 1-argument natives (the arg ends up in A either way) but wastes 2 instructions per native call and is fragile: if arg-slot loading order in the `for` loop is ever changed, this trailing re-load could load the *wrong* staged value into A right before the call. Worth a closer look / test-case verification before relying on multi-argument native calls in production hooks.
- `bpf_builder_free()` destroys `string_region` even though it isn't created by `bpf_builder_init()` (`bpf_builder.c:31`) — `string_region` is a frontend-owned region (per `design.md`'s 5-region model), so destroying it from the *backend's* free function couples backend teardown to frontend lifetime in a way that isn't obvious from `bpf_builder.h`'s API surface. This works in the demos because `bpf_builder_free()` is always called after `frontend_destroy()` in the same process (see `nodeA/src/compiler.c:90,127`), but it's an implicit ordering dependency, not an enforced one.

### 2.4 `cdb` tool (`cdb/cdb.cpp`, `cdb/main.cpp`) — separate C++/Clang LibTooling instrumentation tool

Read in full (621 + 13 lines). Confirmed purpose: `cdb` is a source-to-source auto-instrumentation tool, architecturally and toolchain-wise completely separate from the rest of `lib-cBPF` (C++ against Clang's `RecursiveASTVisitor`/`Rewriter`/`Tooling` APIs, vs. the rest of the project's plain embedded C). Given a project root, it:

1. Recursively copies the entire project tree into a `process/` output directory (`copy_tree()`), explicitly excluding any path containing an `ccbpf`, `lib`, or `mg` path segment (`is_ccbpf_path`/`is_lib_path`/`is_mg_path`, `cdb.cpp:32-69`) — i.e., it instruments the *application* code, not the ccbpf runtime/compiler itself.
2. Parses each `.c` file with Clang and, via a small rule-engine (`InsertRule{Condition, TemplateGen, InsertPos}`), inserts: (a) `ccbpf_system_init(); register_hooks();` at the top of `main()` in `main.c` (`CondMainInit`/`TempMainInit`), and (b) a per-function entry-trace snippet (`__ccbpf_ctx[...]; HOOK_LINE(__ccbpf_ctx, "hook_trace");`) at the top of every other function body, once per canonical `FunctionDecl` (`CondFuncEntry` dedups via a `SmallSet<uintptr_t>` of canonical-decl pointers, `cdb.cpp:379-392`), plus a symmetric exit-hook rule before each `return` (partially read; `CondFuncExitBeforeReturn` begins at line 427, matching pattern established by the entry-hook rule).
3. Writes the rewritten sources back into `process/`, leaving the original tree untouched.

This means `cdb` is a generator of a synthetic, always-on `"hook_trace"` hook name injected at (seemingly) every function boundary in the target application — a blunt, coarse-grained instrumentation strategy (function-entry/exit tracing everywhere) rather than a targeted one (instrument only specific call sites). No config surface was found in the ~run of the file for selecting *which* functions to instrument beyond the blanket "every function not under ccbpf/lib/mg" rule; this could be a real cost concern for constrained MCU targets if `cdb`-instrumented code were ever deployed rather than used purely as a development/analysis aid. `main.cpp` (`cdb/main.cpp`) is a 13-line CLI wrapper taking a single `project_root` argument — no flags to control instrumentation scope were found.

### 2.5 Vendored `mg`/`lib` fork vs. `libmg` — recheck per follow-up request

A full recursive diff (`diff -rq libmg/{mg,lib} lib-cBPF/{mg,lib}`) confirms `lib-cBPF` vendors an independent copy, not a shared build dependency: `rbtree.c`, `hashmap.h`, `link_list.c`, `mg_alloc.c`, `heap.h`, `memalloc.c`, `membit.c` are byte-identical between the two trees; `lib-cBPF/lib/include/` additionally has one extra file (`common.h`) not present in `libmg`. Two files differ:

- `heap.c` — `lib-cBPF`'s copy widens `PTR_SIZE` from `uint32_t` to `uint64_t` and enlarges `CONFIG_HEAP` from `12*1024` to `60*1024`, plus adds one extra `printf("memory: %lu\r\n", the_heap.all_size);` diagnostic line. This is a deliberate, reasonable adaptation (a compiler's working set is larger than a typical embedded heap workload) and not a functional divergence in the allocation algorithm itself.
- `mempool.c` — this is a genuine functional rewrite, not just a tuning change, and it removes a safety check `libmg-sha.md` §2.4 specifically called out as the one existing good precedent:
  - `libmg`'s `mem_pool_free()` (reviewed in `libmg-sha.md` §2.4) opens with `if (!blk->used) { return; }` — an explicit double-free guard.
  - `lib-cBPF`'s `mem_pool_free()` has no such check: it unconditionally sets `blk->used = 0` and proceeds to re-link the block into the free list by walking `next` pointers looking for the next used node. A second `mem_pool_free()` call on the same pointer will re-run this same logic against an already-freed (and already-relinked) node, corrupting the intrusive free list — the exact double-free failure mode `libmg-sha.md` used `mempool.c` as the counter-example to.
  - The rewrite does add genuine improvements elsewhere: an intrusive `next` pointer per node (`struct pool_node` gains a `next` field) makes free-list-position lookup O(1)-per-neighbor instead of a full list scan, and `amount`/`remain_node` are narrowed to `uint8_t` (a deliberate size-vs-capacity tradeoff, capping pools at 255 blocks). But `mem_pool_create()` also drops the `amount == 0 || size == 0` input-validation check present in `libmg`'s version, and `mem_pool_alloc()`'s `if (!pool)` NULL-check was moved *after* the free-list traversal in the diff rather than before it (needs a second look at exact operator precedence in context — flagged here as a candidate off-by-order issue rather than a confirmed one, since the `if (!pool) return NULL;` in the actual read-back source at `mem_pool_alloc:96-97` does appear before the free-list access at line 99, so this concern is not confirmed on closer reading of the full file — only the `amount==0`/`size==0` validation removal and the double-free-guard removal are confirmed regressions).
  - `mem_pool_free_nodes()` (a read-only accessor for `remain_node`, present in `libmg`) was also dropped entirely from `lib-cBPF`'s copy — no equivalent replacement found in the header (`lib-cBPF/mg/include/mempool.h`).

Conclusion for this sub-section: `lib-cBPF` is not "libmg plus new code" — it is a divergent fork of two files within the shared `mg`/`lib` layer, and that divergence has already dropped a safety property `libmg-sha.md` recommended keeping. If μE-OS ever adopts both `libmg` (as the general SHA heap, per the v1.4.0 roadmap item) and `lib-cBPF` (as this proposed feature) in the same firmware image, the two components' `mempool.c` implementations are binary-incompatible in behavior (though not necessarily in link-time symbol collision risk, which was not checked here) and the double-free regression in `lib-cBPF`'s copy should be fixed to match `libmg`'s guard before any shared deployment, rather than assuming `lib-cBPF` inherited `libmg`'s hardening.

### 2.6 VM / hook system / `.ccbpf` loader (`ccbpf.c`, `bpf_filter.c`, `cbpf.h`, `bpf_format.h`)

This section summarizes source-verified findings from direct reading of the actual (not documented) VM implementation — the most safety-relevant part of the codebase since it is the only part designed to run resident on an MCU target:

- Bounds-checked memory access: all classic-BPF load instructions (`LD`/`LDX` with `ABS`/`IND` modes) are checked against the packet buffer length (`buflen`) before dereferencing; scratch-memory accesses (`LD|MEM`, `LDX|MEM`, `ST`, `STX`) are checked against `CCBPF_STACK_SIZE` (512 bytes, per `cbpf.h` — note: `design.md` documents this as 10 KB, a doc/source discrepancy).
- Static validation is real: `bpf_validate()` checks all jump targets are within instruction-array bounds, checks `ST`/`LD|MEM` slot offsets are non-negative and in-range, rejects `BPF_ALU|BPF_DIV|BPF_K` with a literal `k==0`, and requires the final instruction to be class `BPF_RET`. This substantiates the README's "Safety: Language + VM limits" claim with actual enforcement, not just documentation.
- Asymmetry: `bpf_validate()` rejects compile-time-zero `DIV` but not compile-time-zero `MOD` (only `DIV` is checked at `k==0`), even though the interpreter has a runtime zero-check (`goto err`) for both `DIV` and `MOD`, `K` and `X` forms alike. Minor inconsistency between the static and dynamic safety nets — cheap to fix (mirror the existing `DIV` check for `MOD`).
- `BPF_COP` native-call dispatch has a function-pointer-identity special case: the interpreter's generic `BPF_MISC|BPF_COP` handler does `if (e->fn == native_migrate)` to detect the one native function (`native_migrate`) that should return `CCBPF_MIGRATE` instead of continuing execution — a fragile way to special-case one entry in an otherwise generic native-call table (a dedicated status/id field on `native_entry` would be more robust against, e.g., a future refactor that wraps or copies function pointers).
- Unknown native `func_id` fails silently: if `BPF_MISC|BPF_COP`'s `k` doesn't match any registered `native_entry`, the VM sets `A=0` and continues, whereas a genuinely unknown *opcode* (the `default:` case) returns `CCBPF_ERROR`. This means a hook program compiled against a native ABI that the loaded firmware doesn't (yet, or no longer) implement will run to completion silently producing wrong results, rather than failing loudly — worth hardening to `CCBPF_ERROR` for the "no such native" case too.
- `prog->entry` (from the `.ccbpf` header) appears unused: it is parsed and stored on load (`ccbpf_load_from_memory`), but `ccbpf_run_frame()` always starts execution from a zeroed `ccbpf_ctx` (`pc=0`) — the field does not appear to seed the VM's initial program counter anywhere in the read source. Plausibly a forward-looking field for a not-yet-implemented multi-entry-point feature, but as-is it's dead data; worth a direct question to the maintainer before calling it a bug outright.
- Migration is pack/unpack, not automatic: `ccbpf_ctx_pack`/`unpack` do a flat `heap_malloc`+`memcpy` of the entire fixed-size `struct ccbpf_ctx` (always `sizeof(ccbpf_ctx)`, i.e. always copies the full 512-byte scratch buffer regardless of how much of it a given program actually uses — a minor bandwidth inefficiency for the demo's UNIX-socket transport, more relevant if migration were ever done over a constrained radio link). Actual node-to-node migration is orchestrated entirely by the demo application (`nodeC`/`nodeD`, confirmed by direct source read — see §2.7), not by the library itself; `ccbpf_run_frame()` treats a `CCBPF_MIGRATE` status as an in-place `continue` within a single call, so "migration" inside one process is a no-op unless the caller explicitly packs, transmits, and re-loads the context elsewhere, exactly as `nodeC`/`nodeD` do.
- Robust loader error-unwinding: `ccbpf_load_from_memory()` correctly frees already-allocated strings on a later allocation failure mid-loop — solid defensive C, better than the compiler backend's `abort()`-first approach in §2.3.
- Unaligned-read safety: `extract_short_raw`/`extract_long_raw` use `memcpy`-based helpers rather than unsafe pointer casts, avoiding undefined behavior on strict-alignment MCU targets (e.g. Cortex-M) — a detail easy to get wrong and correctly handled here.
- Doc/source discrepancies (design.md / usage.md vs. actual headers, all confirmed by direct reading of `cbpf.h`/`bpf_format.h`/`vm/bpf/include/ccbpf.h`):
  1. `CCBPF_STACK_SIZE`: documented as 10 KB, actual 512 bytes.
  2. `struct CCBPF_Header`: design.md omits the actual `version`/`flags` fields (confirmed present and populated with real values — `hdr.version=1; hdr.flags=0;` — in `bpf_builder.c:87-88`'s `ccbpf_pack_memory()`).
  3. `compiler_init()` arity: design.md documents 4 params; usage.md's worked example calls it with 3; the actual demo call sites (`nodeA/src/compiler.c:75`, `nodeC/src/test.c:78`) both use 4 arguments (`compiler_init(16, 30*1024, 1*1024, 15*1024)`), confirming design.md's signature is the accurate one and usage.md's 3-arg example is the stale one.
  4. `struct ccbpf_program`: usage.md shows `map_count`/`maps[CCBPF_MAX_MAPS]` fields not present in the actual `cbpf.h` struct — maps are in fact implemented as a separate native-call-mediated hashmap per map ID (confirmed in `nodeB/src/test.c:145-201`'s `get_map()`/`native_map_lookup`/`native_map_update`, using a fixed `g_local_maps[MAX_LOCAL_MAPS]` array of `hashmap`s keyed by `HASHMAP_KEY_INT`), entirely outside the `ccbpf_program` struct and outside the library itself — map storage is a host-application responsibility, not a library-provided feature, which usage.md does not make clear.
  5. `struct hook_entry`: usage.md implies programs link directly (`{name, ccbpf_program* head}`); actual code uses a `struct hook_node{prog, next}` wrapper list, i.e. `hook_entry{name, hook_node* head}`.
  6. usage.md's example workflow never calls `ccbpf_system_init()` before `hook_attach()`, but the actual demos (`nodeB/src/test.c:235`, `nodeC/src/test.c:139`, `nodeD/src/test.c:81`) all call it first — it initializes the required `hook_table`/`native_table` hashmaps and is a required step usage.md omits.

### 2.7 Demo wiring (`nodeA`–`nodeD`) — confirmed by direct source read

- Dynamic injection demo (`nodeA`/`nodeB`): `nodeA/src/compiler.c` is a CLI that either compiles a `.c` source to a `.ccbpf` image (`compile_to_bpf()`, wiring together lexer→parser→IR→backend exactly as documented) or sends an `ATTACH`/`DETACH` command over a `SOCK_DGRAM` Unix socket (`/tmp/ccbpf_hook.sock`) to a running `nodeB` process. `nodeB/src/test.c` is the long-running "host" process: it registers 7 native functions (`ntohl`/`ntohs`/`print`/`print_str`/`map_lookup`/`map_update`/`now_ms`), registers one hook (`hook_udp_input`), and in its main loop synthesizes a fake UDP packet, runs the hook against it (`hook_run`), and separately polls the control socket non-blockingly for `ATTACH`/`DETACH` commands (`hook_process_control_messages`) — confirming the "attach/detach a running hook without reflashing" claim is real and works end-to-end via this out-of-band control channel, not just documentation.
- Migration demo (`nodeC`/`nodeD`): `nodeC/src/test.c` compiles and runs a program via repeated `ccbpf_vm_step()` calls (64-instruction budget per call, matching `ccbpf_run_frame`'s internal chunking), and on receiving `CCBPF_MIGRATE` from the interpreter, packs the VM context (`ccbpf_ctx_pack`) and streams `{img_len, img, ctx_len, ctx_buf}` to `nodeD` over a `SOCK_STREAM` Unix socket (`/tmp/ccbpf_migrate.sock`). `nodeD/src/test.c` receives this, reloads the same image, unpacks the context (`ccbpf_ctx_unpack`), and resumes stepping from where `nodeC` left off. This is a genuine (if locally-simulated, same-machine) proof of the pack/unpack migration primitive described in §2.6 — actual cross-hardware migration would require replacing the Unix-domain-socket transport with whatever inter-node link μE-OS's target topology provides (e.g. UART/CAN/radio between MCUs), which is out of scope of what's demonstrated here.

| 14 | `temp_slot()` has no bounds check against `CCBPF_STACK_SIZE` at compile time (only caught later by `bpf_validate` on-target) | Late failure detection | `layout.c` |

Positive/well-designed aspects (balancing the above): bounds-checked packet and scratch-memory access in the interpreter; a real static validator substantiating the "Safety" claim; alignment-safe unaligned-read helpers (`memcpy`-based, not pointer-cast); careful cleanup-on-partial-failure in the `.ccbpf` loader; correct reuse of the region-allocator model for compiler phase memory (validating that design choice, previously questioned as a general-purpose allocator in `libmg-sha.md`); a working, source-confirmed end-to-end demo for both showcased capabilities (dynamic hook injection and cross-process execution migration).

## 4. Integration considerations for μEDP / μE-OS

### 4.1 On-target footprint is small; the compiler and `cdb` are not on-target components

Only the VM/hook/loader layer (`bpf_filter.c`, `ccbpf.c`, plus the shared `mg`/`lib` allocator) needs to run resident on an MCU. README's own figures (1–2 KB RAM for a VM running <200 instructions) are consistent with this being lightweight enough for the STM32F103-class targets already referenced elsewhere in this repo's reviews. The compiler (frontend/IR/backend) and `cdb` are host-side developer tools — akin to how `pltf/pycdscriptor` (see [`docs/review/pltf-impl.md`](pltf-impl.md)) is a host-side codegen pipeline, not firmware. Any roadmap entry for this feature should scope the "ship on μE-OS" claim to the VM/hook layer only, with the compiler treated as an SDK/toolchain deliverable.

### 4.2 Error-handling convention mismatch

μEDP's existing PAL conventions (`RETR_STAT`, `pal_sys_fatal()`/`UEDP_PANIC()`, per `libmg-sha.md` §4.2) are more structured than this codebase's current `abort()`/`exit(1)`/`while(1){}` backend error handling. Since the backend is host-tool-only, this is lower priority than similar concerns would be for on-target code, but the VM layer itself is clean enough already (returns `enum ccbpf_status`) to slot into a future `pal_bpf_*` wrapper API following the same shape `libmg-sha.md` §4.2 proposed for `pal_sha_*`.

### 4.3 Shared allocator dependency needs reconciling before co-deployment

Per §2.5, if μE-OS ever ships both the v1.4.0 SHA heap (from `libmg`) and this proposed BPF feature (`lib-cBPF`) in the same firmware image, their `heap.c`/`mempool.c` copies are currently not the same code — sizes differ (deliberately) and safety behavior differs (accidentally, in `mempool.c`'s case). This needs an explicit decision: either (a) `lib-cBPF` is refactored to depend on the *same* hardened `pal_sha_*`-wrapped allocator proposed in `libmg-sha.md` §4.2 rather than vendoring its own fork, or (b) the fork is kept separate but the double-free regression in §2.5 is fixed to match `libmg`'s guard, so at minimum the two forks don't have *different* safety postures for nominally the same data structure.

### 4.4 No existing μEDP call site to compare against

Like the `libmg` SHA review noted in its §4.1, μEDP core currently has no dynamic-allocation or dynamic-code-loading precedent — a BPF-hook feature would be a new capability, not a refactor, carrying no migration risk to existing subsystems but also no existing integration convention to follow beyond what this review and `libmg-sha.md` jointly establish.

## 5. Open questions for the roadmap owner

1. Scope of "adopt lib-cBPF": is the goal to ship only the VM/hook/loader layer on-target (per §4.1), with the compiler treated as an external SDK tool (like a cross-compiler), or is there a use case for on-target compilation as well? This materially changes how much of §2.1–2.4's findings need fixing before v-next.
2. `libmg` vs. `lib-cBPF`'s forked allocator: per §2.5/§4.3, should `lib-cBPF` be refactored to consume the same hardened SHA allocator once v1.4.0 lands, or does it stay an independent fork (in which case the double-free regression in finding #16 should be fixed on its own timeline, independent of the v1.4.0 SHA work)?
3. `prog->entry` field (finding #9): confirm whether this is dead/forward-looking data or an actual bug where multi-entry-point `.ccbpf` images silently always execute from instruction 0.
4. Native-call ABI failure mode (finding #10): should an unknown `func_id` be promoted from a silent `A=0` to a hard `CCBPF_ERROR`, matching the "unknown opcode" behavior? This is a compatibility-vs-safety tradeoff — a firmware image with a smaller native table than the hook program expects would currently degrade silently rather than reject the hook at attach time.
5. `cdb`'s scope (finding #17): is blanket function-entry/exit tracing across the entire non-library codebase an intended production feature, or a development/debugging-only tool that should never ship instrumented code to a released target?
6. Version/name for this roadmap entry: this review proposes tentative "μE-OS vNext: The Dynamic Hook / BPF Extension" naming at the end of `docs/ueos-roadmap.md` (see that document) — confirm or rename before this becomes a tracked checklist item.

## 6. Conclusion

`lib-cBPF` demonstrates a real, working dynamic-hook-injection and execution-migration capability with a genuinely safety-conscious VM/loader layer, verified by direct source reading rather than documentation alone. It is not yet roadmap-ready as-is: the compiler backend is prototype-grade (crash-on-error, debug-output-by-default), several usage.md examples are stale relative to the actual API, and — per the specific recheck requested for this review — its vendored copy of `libmg`'s allocator layer has already regressed one safety property (`mempool.c`'s double-free guard) that `libmg-sha.md` identified as worth keeping. None of these are fundamental design flaws; they are the kind of hardening and doc-sync work expected of a feature that has not yet been through a roadmap cycle. This review, together with the proposed new entry appended to [`docs/ueos-roadmap.md`](../ueos-roadmap.md), is intended to give the roadmap owner enough concrete detail to decide whether and when to schedule it.
